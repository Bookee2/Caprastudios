What Animate.css can teach us

Animate.css is the best-known library of ready-made CSS animations: about 100 named keyframes (bounce, fadeInUp, headShake and so on) that you switch on by adding a class. We shouldn't install it. The parts worth taking are its system: a few motion tokens, a reduced-motion rule that respects end states, and rules about when to animate at all.

Short versionTake three ideas: duration as one token with multipliers, the "1 ms, not none" reduced-motion rule, and a short list of named, purposeful animations. Leave the library itself. Its keyframes come from 2015–2020 browsers, its 1-second default is too slow for UI, and the Hippocratic licence isn't a standard open-source licence.

What the repo actually is

Small

One file of variables, one base file, and one file per animation in 16 folders (fading_entrances/, attention_seekers/…). PostCSS joins them and adds the animate__ prefix.

Stable

v4.1.1 dates from 2020. The last commit, from March 2024, was a docs typo. It is finished rather than maintained, so it shows nothing of scroll timelines, view transitions or WAAPI.

Licensed unusually

Hippocratic License 2.1 is an ethical-use licence, not an OSI one. Before copying keyframes into client work, rewrite them or check the terms.

1. Motion as tokens, not numbers

The whole library runs from three custom properties. Every speed and delay is a multiple of them:

:root { --animate-duration: 1s; --animate-delay: 1s; --animate-repeat: 1; }
.animated        { animation-duration: var(--animate-duration); animation-fill-mode: both; }
.animated.fast   { animation-duration: calc(var(--animate-duration) * 0.8); }
.animated.slow   { animation-duration: calc(var(--animate-duration) * 2); }
.animated.delay-2s { animation-delay: calc(var(--animate-delay) * 2); }

Changing one variable re-times the whole site, or one component when you set it on that component's element (el.style.setProperty('--animate-duration','.5s')).

Where we are

We have one shared curve, --ease: cubic-bezier(.2,.8,.2,1), in assets/site.css, but four other hard-coded curves across site.css, page-transitions.css and motion-page.css. We have no duration token, and site.css alone uses eight durations: .25, .3, .4, .45, .5, .6, .9 and 1.2 s.

Suggestion: add --dur (≈ .45s) with --dur-quick and --dur-slow derived from it, plus --ease-out and --ease-in-out. Then fold the existing values into those tokens.

Try it: one knob re-times everything

The two fadeInUp chips stay in step at any setting because "slow" is a multiple, not a separate number. With reduced motion turned on, they jump straight to their final state.

2. Reduced motion: shorten to 1 ms, don't switch off

@media print, (prefers-reduced-motion: reduce) {
  .animated { animation-duration: 1ms !important; transition-duration: 1ms !important;
              animation-iteration-count: 1 !important; }
  .animated[class*='Out'] { opacity: 0; }
}

This is the cleverest part of the library. With fill-mode: both plus a 1 ms run, every element still lands on its final frame, and animationend and transitionend still fire. animation: none leaves an element in its un-animated style, which for an entrance often means invisible, and code waiting for an end event never resumes. The library also applies the same rule to print.

Where we are

site.css line 326 uses animation:none!important; transition:none!important. That's safe today: our reveals are transitions to class-set end states, and no script listens for end events. It breaks as soon as someone adds a keyframe entrance that starts at opacity:0. Switching to the 1 ms form now is a two-line change that prevents it.

Our pond, governor and film already go further than the library with still frames, off-screen pausing and a footer motion switch. Keep that approach.

3. A vocabulary sorted by purpose

Its folders are its design guidance: entrances, exits and attention seekers. The docs say attention seekers are for "something special" only, entrances and exits exist to explain a change of state, and infinite loops "should be avoided".

A short named set matters more than the effects themselves. "Use rise" is a decision; "add some animation" isn't.

4. Smaller craft lessons

Hand-tuned keyframes

bounce changes its timing curve within each keyframe and adds a little scaleY squash at each landing. headShake shrinks each swing (−6, 5, −3, 2 px) and finishes at 50%, leaving the second half still. Decaying amplitude is what makes it feel physical.

Set the pivot

Each animation sets its own transform-origin: bounce from center bottom, swing from top center. The pivot does as much work as the curve.

Promise wrapper

The docs' animateCSS(el, name) adds the classes, waits for animationend with {once:true}, removes the classes and resolves a promise. It's a good pattern for chaining. Today, el.animate() with .finished does the same without class juggling.

Its "gotchas" still apply

Inline elements can't be animated (use inline-block). Moving elements create scrollbars (clip the parent). Don't animate html or body. Don't animate large areas.

What's outdated, so don't copy it

  • 1 s default. That's right for showpieces but slow for interface. Use about 200–450 ms for UI.
  • translate3d(0,0,0) everywhere. This GPU-promotion trick predates modern compositors. Plain translate, scale and rotate are cleaner and stack independently. We already use them.
  • Huge fixed distances. backInDown starts at -1200px, so it behaves differently on every screen size. Use small distances or percentages.
  • Class-per-animation with a fixed delay ladder. Steps like delay-1s…5s are clumsy. A --i custom property for stagger, which we already use, is better.
  • Nothing tied to scroll or navigation. We're past it here: animation-timeline: scroll() drives the nav progress bar and view transitions handle page changes.
